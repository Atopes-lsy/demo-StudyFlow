# GitHub 协作规范

## 1. 分支与职责

| 分支 | 用途 |
| --- | --- |
| main | 稳定演示与作业版本 |
| dev | 日常集成与共同联调 |
| feature/home | 组长的契约、计划校验与核心测试，沿用名称 |
| feature/task | 组员 1 的首页、任务、记录、本地数据 |
| feature/record | 组员 2 的模型配置、接入和 AI 页面，沿用名称 |

远程分支已经存在，本地不必预先创建所有分支。工作前确认最新工程与契约已合入 `dev`；不能从过期文档分支各自新建第二套工程。默认不直接修改 `main`。

## 2. 开始开发

先保存已有工作并确认当前分支状态；以下命令仅用于对应场景，不要用强制覆盖解决本地改动。

```text
git fetch origin
git switch dev
git pull --ff-only origin dev
```

本地不存在 `dev` 时，可用 `git switch --track origin/dev`；本地不存在功能分支时，同样跟踪已有远程分支。现有功能分支应在保存工作后合并最新 `origin/dev`。

## 3. Issue 与验收

| 任务 | 负责人 | 交付 |
| --- | --- | --- |
| 共享契约和固定假数据 | 组长 | 三人能按一致输入输出独立实现 |
| 计划解析、规则校验和核心测试 | 组长 | PLAN 测试集与可定位错误 |
| 工程导航、首页、任务与存储 | 组员 1 | 基础业务、本地恢复与统计一致 |
| 学习记录、批量保存与防重复 | 组员 1 | 记录恢复、确认前零写入和单次保存 |
| 模型设置、会话 Key 与模型适配 | 组员 2 | BYOK 配置、脱敏、联网测试替身 |
| AI 交互与请求状态 | 组员 2 | 生成、编辑、取消、错误、旧响应拦截 |
| 测试、报告与演示 | 每人 | 自己模块的证据和段落 |
| MCP 最小验证 | 基础验收后决定 | 最多两个只读工具的协议证据 |

Issue 写清依赖、允许改动的模块、输入输出、假数据、验收用例和截图要求。不把“AI 生成了代码”当成关闭条件。

## 4. 提交与评审

1. 小步提交，PR 只覆盖对应 Issue；接口调整单独说明。
2. 作者运行自己模块的测试，记录环境与复现步骤。
3. 组员互审常规页面与文档；共享契约、凭据、校验、保存一致性请组长重点评审。
4. 作者修复测试失败和自己 PR 的冲突；跨模块问题由相关成员共同处理。
5. 合入 `dev` 后同步功能分支，三人共同联调，不让组长补做全部测试。
6. 基础验收完成后，组长确认稳定版本进入 `main`。本次文档更新不自动提交、推送或改分支。

PR 使用仓库已有模板，并补充关联 Issue、修改范围、执行用例、证据、未验证项和接口影响。未运行的测试必须明确标记。

## 5. 仓库卫生

不提交真实 Key、签名文件、`local.properties`、构建产物和个人敏感数据。截图与网络错误先脱敏；敏感信息一旦推送，删文件不足以消除泄露，须撤销凭据并处理历史。

每人撰写自己的提交记录、报告段落和感想；贡献按实际实现说明。GitHub Issues、规则保护和任务指派是否已配置以实际页面为准，不凭文档宣称完成。
